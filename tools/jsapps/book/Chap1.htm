Along the way you'll meet classes, JavaScript's way of making many objects of the same kind, and Maps, a better kind of object for looking things up.

Planning an application

Snake, at the end of the first book, was small enough to plan in your head. An application isn't: before long it has a dozen windows, menus and dialogue boxes, and it's easy to lose track of what goes where. So start by writing down two things.

What it remembers. An address book remembers contacts. For each one:

title, first name, surname, company, job title,
address, postcode,
work, home and mobile telephone numbers,
email address, web address, birthday,
category (Family, Friends, Work or Other), notes
What happens. The things a person does with it, in their words:

see the contacts in a list, sorted by name
choose one or more of them
add a contact; change one; delete some
find the contacts that match a word
sort by surname, first name or company
keep address books in files, and open several at once
swap contacts with other programs
undo a mistake
Those lists are the plan for Part One: each chapter makes one or two lines of it work.

The model and the view

Look at the two lists again. The first is about information; the second is mostly about windows - lists, choosing, menus, files. The most useful decision you can make about an application is to keep those two apart:

The model
holds the information and the rules about it: the contacts, how they're sorted, what makes a contact valid. It knows nothing about windows, menus or the mouse.

The view
shows the model on the screen and lets the person change it. It asks the model for what to show, and asks the model to make changes.

Keeping them apart pays off again and again. The model can be tested without opening a window (you'll do that later in this chapter). Several windows can show the same model at once. And the model can be used in another program: in Part Two, !Organiser's address section uses !Contacts' model without a single change.

In !Contacts the model is a module called Model, and the first view is MainWindow.

Classes

In the first book, when a program needed several things of the same kind - Snake's cells, Doodle's lines - it made objects with { ... } and kept them in arrays, and wrote functions to work on them. That works well for simple things. For something with its own information and its own operations, such as an address book, JavaScript has a neater way: a class.

A class is a description of a kind of object: what information each one holds, and what it can do. Here is the start of the Book class, lines 10 to 32 of Model:

There's a lot that's new here, so take it a piece at a time.

class and new

class Book { ... } describes what a Book is. It doesn't make one: you do that with new, as !RunImage does:

const book = new Book();
Each new Book() makes a separate address book, with its own contacts. That's why a class is better than a module's variables for this: in chapter 7 !Contacts will open several address books at once, and each will be a Book of its own.

You've been using classes since the first book without knowing it: new Menu(...) and new Date() make objects of the classes Menu and Date.

The constructor and this

The constructor is a function that runs when a new Book is made, to set it up. Inside it, and inside all the class's functions, this means "the Book this is happening to". So this.contacts = new Map() gives the new Book a property called contacts, and this.nextId = 1 another one. Every Book has its own contacts and its own nextId.

Methods

The functions written inside a class - get, all, add, list - are its methods, just like the methods of arrays and strings you used in the first book. You call them with a dot: book.add({ first: 'Ann' }). Notice that you don't write function in front of them, and that there are no commas between them.

Getters

get size() { ... } is a method you use as if it were a property, without brackets: book.size. It's worked out each time you ask, so it's always right. (Arrays' length works the same way.)

extends and super

class Book extends Emitter says a Book is a special kind of Emitter: it can do everything an Emitter can (you'll see what that is shortly), and more. Emitter is the parent class. A class that extends another must call super() at the start of its constructor, to let the parent set up its part of the object first.

Maps

The contacts are kept in a Map. A Map is like an object used for looking things up: it holds pairs of a key and a value, and finds the value for a key quickly. Here the key is each contact's id, a number that's different for every contact, and the value is the contact:

const m = new Map();
m.set(7, { first: 'Ann' });      // key 7
m.get(7)                         // { first: 'Ann' }
m.has(7)                         // true
m.delete(7);
m.size                           // how many pairs
[...m.values()]                  // all the values, as an array
Why not keep the contacts in an array, as the first book would have done? Because !Contacts will often need to find one contact among many - the one being changed, the one being deleted - and an array would have to be searched from the start every time. With a Map, this.contacts.get(id) finds it at once, however many there are.

Why an id, and not the contact's name? Because names change (Ann Smith marries and becomes Ann Jones), and two people can have the same name. An id is fixed, and belongs to one contact only.

Adding a contact

add takes an object of fields, such as { first: 'Ann', last: 'Smith' }, and has two things in it you haven't seen before:

  • fields.id ?? this.nextId: ?? gives the value on its left, unless that is null or undefined, in which case it gives the value on its right. So a contact that already has an id keeps it, and a new one gets the next free number.

  • { ...fields, id } makes a new object with all of fields' properties (..., spread, copies them in) and then an id. Making a new object, rather than adding the id to the one it was given, means the Book has a contact of its own that nobody else can change behind its back.

all() uses spread too: [...this.contacts.values()] makes an array of every value in the Map.

Sorting names

The rest of Model is two small functions for showing a contact, and the rule for sorting:

nameOf uses || in a way the first book didn't: a || b gives a if it counts as true, and otherwise b. So c.last || c.first || c.company || '(no name)' gives the first of them that isn't empty.

compare is a compare function for sort, as in chapter 5 of the first book. It compares surnames (or companies) first, then first names, and if both are the same, the ids, so the order is always the same. Instead of < it uses localeCompare, a string method that compares the way a dictionary does: < puts every capital letter before every small one, so "de Vere" would come after "Young", but localeCompare puts it among the Ds. With { sensitivity: 'base' } it also counts a capital and a small letter, or a letter with an accent and one without, as the same, so "Smith" and "smith" are equal.

compare isn't exported: it's the Book's own business how it sorts.

The change event

Every time add adds a contact, it calls this.emit('change', ...). That's what a Book gets from being an Emitter. Emitter is the first module of the toolkit:

An Emitter keeps a list of functions to call for each kind of event. on('change', fn) adds a function to the list for 'change'; emit('change', data) calls every function on it. So any part of the program can ask to be told when the Book changes, and the Book doesn't need to know who's asking.

Two details:

  • The listeners for each event are kept in a Set, which is like an array that can't hold the same thing twice, and can remove things quickly: add, has and delete work as they do for Maps.

  • on returns a function. Calling it removes the listener again - useful when a window that was listening is closed.

Nothing listens to the Book in this chapter. In chapter 4 the list in the window will listen, so it can redraw itself whenever the Book changes, whoever changed it.

Summary

  • Plan an application by writing down what it remembers and what happens.

  • Keep the model (the information and its rules) apart from the view (the windows).

  • A class describes a kind of object; new makes one; the constructor sets it up; this is the object; its functions are methods; get makes a method you use like a property.

  • extends makes a class a special kind of another; call super() first in its constructor.

  • A Map finds a value by its key quickly; a Set holds things without repeats.

  • a ?? b gives b only if a is null or undefined; a || b gives b if a counts as false; { ...obj } and [...list] copy.

  • An Emitter lets other parts of a program listen for events with on; emit tells them.

  • Test the model with a program of its own, and run it after every change.

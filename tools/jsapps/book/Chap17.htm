The Organiser's notepad pages are typed into with the desktop's TextArea: several lines of text in a window, with a caret, word wrap and scrolling. The Wimp itself only has writable icons, which hold one line. This last chapter builds a text area of your own, TextBox, and puts it in the Notepad in place of the desktop's. You won't need to use it - the desktop's is better - but by the end you'll know how such a thing works, which is the best way to use one well, and the way to build other things the desktop doesn't have.

The example is !Org17: the finished organiser with one module added, TextBox, and two lines changed in NotesPage.

What a text area has to do

Plan it as the Organiser was planned, by what it remembers and what happens:

It remembers
the text (one string, with '\n' between lines), where the caret is (an index into the text), and how far it has scrolled.

It draws
the text, broken into lines that fit its width, on a canvas of its own in the window; and it shows the Wimp's caret at the right place.

It responds to
a click inside it (the caret goes there), and keys while it has the caret: characters are typed in, Backspace takes one away, Return starts a new line, the arrow keys move about.

Everything else - the window, its other clicks and keys - belongs to the program, so the text area must take only what's meant for it.

The text box and its canvas

The constructor keeps the box's position and size, and the text. Object.assign(this, { win, x, y, ... }) (chapter 2) sets several properties in one go.

The box draws on a canvas of its own. document.createElement('canvas') makes one, as it did for printing in chapter 16, but this time the canvas goes into the window: its style says where it's shown, at x, y, and appendChild puts it in win.work, the window's work area - the desktop's way of putting a canvas of your own in a window, where it scrolls with the work area. Its pointerEvents: 'none' lets clicks go through it to the window, which gives them to the program as usual.

First in the queue

The window's events are the next problem. win.on('click', ...) adds a handler to the end of the window's list, and the handlers are called in turn until one returns true. The organiser's own click handler was added long before any text box was made, and it takes every click - so a text box added after it would never see one.

{ first: true }, which chapter 14 showed the desktop's TextArea using, puts a handler at the front of the list instead. The text box's handlers run first; they return true for a click inside the box, or a key while it has the caret, and undefined for anything else, which then goes on to the organiser's handlers as before.

win.on returns a function that takes the handler away again, and the box keeps them all in offs. That matters: a notepad page's box is thrown away when you turn to another page, and a box that left its handlers behind would go on taking clicks and keys for a text that isn't there any more.

Lines that fit

The text is one string; the box shows it as lines. lines() works them out, as a list of where each line starts and ends in the text:

It takes the text up to the next '\n'. If that's too wide - measureText says how wide text is in the canvas's font - it looks for the last space before the end and tries again, and so on until the line fits. (A single word too long for the box is cut wherever it fits.) The next line starts after the newline or space it broke at.

This is called whenever the box is drawn or a key is pressed. Measuring the text each time is slow in principle, but a notepad page is small, and it keeps the program simple: the lines are never out of date.

where() finds the caret's line and how far across it the caret is, in pixels:

findLastIndex is to findIndex what findLast (chapter 10) is to find: it looks from the end of the array, and gives the index of the first item it comes to that passes the test - here the last line starting at or before the caret, or -1 if there isn't one. (Appendix A.)

Drawing, and the caret

First the box makes sure the caret can be seen: if its line is above the top, or below the bottom, of what's showing, scroll changes so it isn't. Every line is then drawn scroll pixels higher than it would be; the ones outside the box simply don't show on the canvas.

The caret is the Wimp's own. wimp.setCaret(win, null, -1, { x, y, h }) gives the window the input focus with no writable icon, and draws the red caret at x, y in the work area, h pixels high. It's the same call !JsEdit and !Edit use. Because the window then has the input focus, the keys come to it - and so to the box's key handler, first.

focus() marks the box as having the caret and draws it. When the caret goes to another window, the window gets a 'losecaret' event, and the box notes that it no longer has it.

Clicks

A click outside the box isn't ours: focused becomes false and the handler returns undefined, so the organiser gets the click. A click inside works out which line was clicked, from the height of a line and how far it has scrolled, then nearest measures the line's text a character at a time to find the character the pointer is over, and puts the caret before it. (So it always rounds to the left: clicking on the right half of a letter puts the caret before it, not after. Comparing with the middle of each character instead would put it on the nearer side.)

Keys

All editing goes through insert(s, n): take n characters away before the caret, put s in, move the caret after it, redraw, and emit 'change'. Typing is insert('a'), Backspace is insert('', 1) and Return is insert('\n'). Having only one way to change the text keeps it easy to get right.

Left and Right move the caret one character. Up and Down move to the line above or below, as near as possible to the same distance across - that's why where() works out x.

Most important is the last line of key's default: any key the box doesn't use returns undefined. F3, Page Up, Ctrl-D and the rest then go on to the organiser, so saving, turning pages and inserting the date still work while you're typing a note. (A text area that took every key would be a trap.)

What the desktop's TextArea does more

TextBox is about 160 lines. The desktop's TextArea, part of the desktop's own source code (about 200 lines, and not on the disc), is built the same way, and adds:

  • More keys: Home and Ctrl-Left (start of the line), Ctrl-Right and Shift-Copy (end of the line), Ctrl-Up and Ctrl-Down (start and end of the text), Copy (delete to the right), and Ctrl-U (delete the line).

  • Pasted text: it listens for the window's 'paste' event.

  • Moving between fields: Tab and Shift-Tab go to the next writable icon or text area in the window, as in any dialogue box, and the Wimp's Tab from a writable icon comes to it. For that, the text areas in a window are kept together (win._textAreas), and only one of them has the caret at a time.

  • Losing the caret properly: it also watches 'caretmove', when the caret moves to an icon in the same window.

  • A readOnly setting, drawn in grey.

  • Sharp text on high-resolution screens: its canvas has more pixels than its size on the screen.

None of these is hard; each is a few lines in the same pattern. That's the point of building one: nothing the desktop gives you is magic, and when it doesn't give you something - a list, a form, a toolbar, a binder, a text box - you now know how to make it.

Where to go next

You've finished both books. Some places to go from here:

  • Make something of your own. The best next step. Start small, plan it the way chapter 1 did, and borrow freely from !Contacts and !Organiser - the toolkit modules were written to be reused.

  • The RISC OS Style Guide (Acorn, 1993; RISC OS Open publish a revised edition) is the reference for how a RISC OS application should look and behave. Appendix D is a checklist drawn from it.

  • The RISC OS Programmer's Reference Manuals describe everything the real Wimp does, in the terms of the original machine. This desktop's interface (appendix C, and book 1's appendix B) is modelled on it, so much of what they say applies.

  • JavaScript goes much further than these books have taken it. A reference such as MDN Web Docs (developer.mozilla.org) describes every part of the language; the language features appendix A lists are a good place to start reading.

  • The desktop's own applications are JavaScript too, in the desktop's source code rather than on the disc. Once you can read !Contacts, you can read them: !Edit, !Draw, !Paint and the rest show how bigger programs are put together.

Happy programming.

Summary

  • A text area remembers its text, a caret index and a scroll position, and works out everything else - the lines, the caret's position - when it needs it.

  • It draws on its own canvas inside the window's work area, and shows the Wimp's caret with wimp.setCaret(win, null, -1, { x, y, h }).

  • Its handlers are added with { first: true } so they run before the program's, and return undefined for anything not meant for it. remove() takes them away again.

  • All changes go through one method, insert, which emits 'change'.

  • Modules with the same shape can be swapped for one another.

Exercises

1 Make Home move to the start of the caret's line, and Copy delete the character to the right of the caret.

2 Add Ctrl-U, which deletes the whole of the caret's line.

3 Let text be pasted into the box.

4 Scroll the box with the mouse wheel. (Windows have a 'wheel' event with dy, the amount to scroll; a handler returning true stops the window scrolling itself.)

5 Harder: a selection. Shift with Left or Right extends a selection from the caret; typing replaces it; it's drawn with a coloured background.

Answers

1 Two more cases in key, before default: 
case 30: this.caret = lines[n].start; break;            // Home
case 0x18B:                                             // Copy
  if (this.caret < this.text.length) {
    this.caret++;
    this.insert('', 1);
  }
  return true;
Copy moves the caret past the character and deletes it as Backspace would.

2 Find the line's ends in the text itself (not the wrapped lines), and cut it out: 
case 21: {                                              // Ctrl-U
  const t = this.text;
  const a = t.lastIndexOf('\n', this.caret - 1) + 1;
  let b = t.indexOf('\n', this.caret);
  b = b < 0 ? t.length : b + 1;
  this.caret = b;
  this.insert('', b - a);
  return true;
}
3 Listen for the window's 'paste' event, first, while the box has the caret, and keep its off with the others: 
win.on('paste', (ev) => {
  if (!this.focused) return undefined;
  this.insert(ev.text.replace(/\r\n?/g, '\n'));
  return true;
}, { first: true }),
4 The 'wheel' event doesn't say where the pointer is, so take it while the box has the caret: in the constructor, 
win.on('wheel', (ev) => {
  if (!this.focused) return undefined;
  const most = this.lines().length * LINE - this.h + 2 * PAD;
  this.scroll = Math.max(0, Math.min(most,
    this.scroll + ev.dy));
  this.drawOnly();
  return true;
}, { first: true }),
- but draw scrolls back to the caret, so split it: a drawOnly() that draws at the current scroll, called by draw after it has made the caret visible. While the box doesn't have the caret, the wheel scrolls the window as usual.

5 Keep a second index, anchor, where the selection started (or null). Shift-Left and Shift-Right (0x19C and 0x19D) set anchor if it's null and move the caret; other movement clears it. In draw, fill the background from Math.min(anchor, caret) to Math.max(anchor, caret) on each line it covers, before drawing the text. In insert, if there's a selection, remove it first. It's the biggest of these exercises - the desktop's own !Edit has a whole module for selections.

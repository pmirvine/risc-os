In this chapter !Contacts learns to add and change contacts, in a dialogue box with a field for each detail. You'll build the third toolkit module, Form, which makes a dialogue box from a list of fields, and use it for the contact's card. You'll also meet Promises, which let a program wait for someone to fill in a dialogue box.

Dialogue boxes

The first book's windows were built icon by icon: { x: 10, y: 40, w: 200, h: 28, ... } for each one. That was fine for a window with three icons, but the contact's card has thirty. Worse, every dialogue box should behave the same way, and the Style Guide is specific about how:

  • Each field has a label to its left.

  • The action buttons go at the bottom right. The default button - the one Return presses - is on the right, and drawn with a thicker border. Cancel is to its left.

  • Return in a field moves to the next field; in the last field, it presses the default button.

  • Tab and Shift-Tab, and the up and down arrow keys, move between fields.

  • Escape is the same as Cancel.

  • If something typed isn't acceptable, say so, and put the caret back in that field.

Getting all that right once, in a toolkit module, is much better than getting it nearly right in every dialogue box. So Form takes a list of fields and does the rest:

const form = new Form(task, {
  title: 'Contact',
  fields: [
    { name: 'first', label: 'First name' },
    { name: 'notes', label: 'Notes', lines: 3 },
    { name: 'category', label: 'Category', choices: ['A', 'B'] },
  ],
  buttons: ['Cancel', 'Save'],
  check: (values) => ...,
});
const values = await form.ask(contact);

The contact's card

The contact's dialogue box is in a module called Card. Double-click a contact in !Contacts3 to open it:

Here is how Card describes it:

Each field has a name (which property of the contact it shows) and a label, and perhaps:

width
the width of the field in pixels, if it shouldn't be the usual 220.

lines
for a field of several lines, such as the address. Form uses the desktop's TextArea for these: a box of text with a caret, which wraps long lines. (Chapter 17 shows how one works inside.)

allowed
the characters that may be typed: telephone numbers may only have digits, spaces, +, brackets and hyphens. Form gives it to the writable icon as an A validation (allowed), a validation string like the R5 border you gave buttons in the first book: A0-9 +()- lets through only those characters (0-9 means any digit), and the Wimp refuses any other key.

choices
a list to choose from with a pop-up menu, instead of typing.

option
an on/off option icon (a tick box). The card has none; chapter 9's Choices box uses them.

help
a line of interactive help for !Help to show.

{ column: 2 } isn't a field: it starts a second column, so the card is wider rather than very tall.

let form = null and, further down, form ??= makeForm(task) make the dialogue box the first time it's wanted and use the same one after that. a ??= b is short for a = a ?? b (chapter 1): it sets form only if it's still null.

How Form builds a dialogue box

Form is the longest toolkit module so far, about 190 lines. Its constructor works out where every icon goes, in two loops. The first makes the fields:

x and y are where the next field goes; each field moves y down by its height, and { column: 2 } moves x to the right of everything so far and y back to the top. For an ordinary field there are two icons: the label, right-justified so the labels line up against their fields, and a writable icon. A field with choices gets a grey, non-writable icon for the choice and a small button beside it with the sprite that pop-up menus use. A field with lines gets only its label here: its TextArea is made after the window.

Each icon is given a name. The desktop lets you find an icon by its name with w.iconByName, so Form never has to count icons.

The second part makes the buttons, from right to left:

A Form can also be told that some buttons don't close the box, with stay: ['Default']: such a button emits a 'button' event instead (the Choices box in chapter 9 needs it).

names.at(-1) is the last button (at counts from the end with a minus number), so the last button in the list is the default, drawn with R6 validation - the thick border - and a little bigger. The others have R5, the ordinary action-button border. [...names].reverse() reverses a copy of the list (reverse changes the array it's used on, and the original is still needed).

The window is made with returnNext: true. That asks the Wimp to move the caret to the next field when Return is pressed, and to pass Return on to the program only in the last field. Tab, Shift-Tab and the arrow keys move between fields anyway, and they move into and out of TextAreas too. "Next" means in reading order - along each row, then down - so in the card, with its two columns, the caret goes from Title to Work phone, then First name to Home phone, and so on. (The Category field isn't typed into, so it's skipped.)

Finally each field is matched with its icon, and a TextArea is made for each field with lines.

Getting and setting the values

get() reads every field into an object: a TextArea's text, an option icon's on-or-off, or a writable icon's text with the spaces at either end removed. (!!x in set turns a value into true or false, as chapter 2 showed.) set(values) does the opposite. Both go through the fields with for...of and destructuring: const { spec, icon, area } of this.fields takes each field entry apart into three variables as it goes.

Waiting for an answer: Promises

Opening a dialogue box is easy. The hard part is what comes next: the program has to wait for the person to click Save or Cancel, and then carry on with what they typed. It mustn't sit in a loop while it waits - as chapter 9 of the first book explained, the desktop would freeze.

You've used the answer already: await. In the first book, await input('Name? ') waited for a line of typing, and await vfs.readText(...) for a file. Both worked because input and readText return a Promise: an object that stands for an answer that isn't ready yet. await pauses the function until the Promise is resolved - until the answer arrives - without stopping anything else.

Form makes a Promise of its own:

new Promise((resolve) => { ... }) makes a Promise, and gives you a function, resolve, that you call when the answer is ready. run opens the box, puts the caret in the first field, and returns the Promise - but keeps its resolve function in this.done. Later, when a button is pressed, finish(result) closes the box and calls it, and that is the moment the program's await gives its answer.

ask is the simple version most programs want: it gives just the values, or null for Cancel: r ? r.values : null (the conditional operator, from chapter 1). done?.(result) calls done only if it isn't null: ?. is optional chaining, and stops quietly if what's on its left is null or undefined.

Buttons, checking and keys

press is called for every button. Cancel finishes with null. For any other button, it reads the values and gives them to the check function, if there is one. If check finds a problem, Form reports it, puts the caret in the field it names, and leaves the box open for the person to put it right. Only when everything's acceptable does the box close. reportError(message) is the desktop's error box, which chapter 2 used for its message.

click tells which icon was clicked by its name. name.startsWith('button:') and name.endsWith('!') are string methods that do what they say; name.slice(7) is the name without its first seven characters (button:), and name.slice(0, -1) the name without its last one (a minus number counts from the end). this.fields.find((f) => ...) gives the first field the function says yes to (or undefined): it's filter that stops at the first one. A pop-up button opens a menu of the choices beside the field, with the current one ticked: popup makes a Menu, turns the field's top-right corner from work-area to screen coordinates with workToScreen (menus are placed on the screen, windows' contents in their work area), and opens it there with wimp.menus.open(menu, x, y, { task }) - the same thing that happens, at the pointer, when you click Menu.

key presses Cancel for Escape, and the default button for Return. (Return only reaches it from the last field, because of returnNext. A TextArea keeps Return for itself, to start a new line.)

Checking a contact

Card's check function is the rules for a contact:

It needs a name or a company, an email address that looks like one, and a birthday that's a real date.

The email address is checked with a regular expression, a pattern for text, written between slashes (the first book used one, /\s+/, to split words). In /^[^@\s]+@[^@\s]+\.[^@\s]+$/: ^ and $ mean the start and end of the text; [^@\s] is any one character that isn't @ or a space (\s is any space; ^ inside brackets means "not"); + means one or more of them; \. is a real dot (a plain . would match anything). So: something, @, something, a dot, something - with no spaces or second @. test says whether the text matches.

Birthdays can be typed the British way, 25/12/1990, or as 1990-12-25, and dateKey turns either into the second form, which is the one !Contacts keeps (it sorts properly, and in chapter 11 the organiser uses the same form for every date). The two patterns are /^(\d{1,2})\/(\d{1,2})\/(\d{4})$/ (one or two digits, a slash, one or two digits, a slash, four digits: \d is a digit, {1,2} means one or two of it, and \/ is a slash, which needs a backslash inside a pattern written between slashes) and /^(\d{4})-(\d\d)-(\d\d)$/. exec is the regular-expression method that gives the parts in round brackets as m[1], m[2] and so on, or null if the text doesn't match. Then const [y, mo, d] = ... destructures an array, taking its first three items into three variables. The conditional operators choose which array: day-month-year for the first form, year-month-day for the second, or an empty one if neither matched. In the middle one, (m = /.../.exec(s)) is an assignment used as a value: an assignment gives the value it assigns, so this sets m and tests it at the same time.

The last line puts the date back together with padStart(2, '0'), which pads a string on the left to two characters with zeros, so 7 becomes 07.

The last check is a neat trick. new Date(year, month, day) makes a date - but JavaScript counts months from 0, so January is 0 and December 11, which is why the code passes mo - 1 (and +y turns the text '1990' into a number). new Date(1990, 1, 31) - the 31st of February - is quietly turned into the 3rd of March, so if the month has changed, the date wasn't real. (Chapter 11 has more to say about dates.)

Adding and changing contacts

editCard, at the end of Card, opens the box with a contact's values and a title, and gives back the new values (with the birthday tidied) or null. Its parameter contact = {} has a default value, as the ListView's key did in chapter 2: if editCard is called without a contact (as it is for a new one), it gets an empty object instead of undefined. MainWindow uses it:

add and edit are async methods, because they await the card. After it closes, focus gives the list window the keyboard back, so the arrow keys work again straight away. A new contact is added to the Book, selected and scrolled into view; a changed one is given to the Book's new update method:

{ ...this.contacts.get(id), ...fields, id } builds a new contact: all the old one's properties, then the new values on top (a later property of the same name wins), then the id. The old object isn't changed. That matters: the card was given the old contact to show, and until Save is clicked, nothing the person types should touch the address book. Cancel simply throws the typing away.

Model also gains CATEGORIES, the list the card's Category pop-up offers, and Check a test for update.

Both methods call refresh() so the list shows the change. That's a little clumsy - every piece of code that changes the Book has to remember to do it - and chapter 4 has a better way.

The menu

Click Menu on the list: there's a small menu with New contact and Change. The ListView's menu event opens it, and the menu is built afresh each time it opens, as in the first book.

Try clicking Menu over a contact that isn't selected. It's selected while the menu is open (the Style Guide's temporary selection), so Change changes that one; when the menu closes without being used, onClose calls the list's endTemporary to deselect it again.

To try the card:

1 Run !Contacts3 and double-click a contact (or select it and press Return).

2 Change the telephone number, and press Return a few times: the caret moves from field to field, across the two columns and down.

3 Type a wrong email address, such as ann.example.com, and click Save. The box stays open, and the caret is in the Email field.

4 Put it right and click Save. The list shows the change.

5 Choose Menu > New contact, fill in a name, and press Escape: nothing is added.

Summary

  • The Style Guide's dialogue boxes: labels on the left, the default button bottom right with a thick border, Cancel to its left, Return to move on (and in the last field to press the default), Escape to cancel.

  • Form (the toolkit) builds a dialogue box from a list of fields; ask() gives the values or null; a check function keeps the box open until the values are acceptable.

  • A Promise stands for an answer that isn't ready yet; new Promise((resolve) => ...) makes one, and calling resolve gives await its answer.

  • Edit a copy: the dialogue box works on its own values, and the model is changed only when the person confirms.

  • New JavaScript: a ??= b, obj?.x and fn?.(), at(-1), startsWith, endsWith, padStart, regular expressions, exec, array destructuring, months counted from 0.

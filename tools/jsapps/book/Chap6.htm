An address book is only useful if you can find people in it. In this chapter the Find field learns to look at every detail of a contact, not just the name, and the list learns to sort itself three ways - by surname, first name or company - chosen from the menu or with F6, as the Style Guide suggests. On the way the searching moves out of the window and into the Book, which is where it should have been all along. The result is !Contacts6.

Rules belong in the model

Chapter 5's Find field did its searching in MainWindow's refresh. That was quick to write, but think about what else will soon want to search or sort the contacts: exporting them (chapter 8), the organiser's Address section (chapter 10), printing a list of them (chapter 16). Each would need its own copy of the rules, and the copies would drift apart. And the rules are hard to test while they're inside a window: Check can't open windows.

So the rules for which contacts match and what order they go in move into the Book. The Book's list method, which used to return every contact in surname order, now takes the search text and the sort order and returns just the contacts to show, in order:

Anything that wants a list of contacts asks the Book for one, and gets the same answer. The window just shows it:

This is the same idea as chapter 4's, from the other side. There, the model told the views when it changed; here, the views ask the model what to show, rather than working it out themselves. Windows show things and pass on what the user does; the model knows the rules.

Named arguments with defaults

list takes an object - book.list({ search: 'smi', sort: 'first' }) - rather than two arguments in a fixed order. Its parameter list takes the object apart:

list({ search = '', sort = 'last' } = {}) {
{ search, sort } in a parameter list is destructuring: it makes two variables, search and sort, from the properties of the object passed in. = '' and = 'last' are defaults, used for a property that isn't given, and the = {} at the end is the default for the whole object, so book.list() still works and means "everyone, by surname". Named arguments like these read well at the call, and adding a new one later (a category, say) doesn't disturb the old calls.

Searching every field

A contact matches if any of its details contains the search text:

Object.entries(c) turns a contact into an array of [name, value] pairs: [['id', 3], ['first', 'Ann'], ['last', 'Smith'], ...]. some is an array method that asks a question of each item in turn and is true as soon as one says yes (the opposite way round from book 1's filter, which keeps every item that says yes). The question is written as an arrow function whose parameter is itself taken apart: ([k, v]) => destructures each pair into k, the name, and v, the value. The id is left out (searching for 3 shouldn't find contact number 3), and String(v) makes sure the value is text before it's searched.

Sorting

Book 1 sorted arrays with a compare function: sort((a, b) => ...) calls it with two items, and it returns a negative number if a should come first, a positive one if b should, and 0 if it doesn't matter. The Book's comparison has more to do: it must follow the chosen order, and when two contacts tie (two Smiths), fall back on something else:

key gives, for a contact, the list of things to compare, most important first: for the surname order, the surname (or the company, for a firm with no surname) and then the first name. The chain of ? : picks the list for the chosen order. The loop compares the two contacts' lists one item at a time, and returns at the first difference; only if everything is the same does it fall back on the ids, so that the order is always the same from one refresh to the next and the list never jumps about.

Each pair of texts is compared with localeCompare, not <. < compares character codes, which puts every capital before every small letter (Zebra before apple) and accented letters after z. localeCompare compares the way a dictionary does, and { sensitivity: 'base' } tells it to take no notice of capitals or accents at all. ?? '' turns a missing detail into empty text, which comes first: that's why, in first-name order, Jam Tomorrow Cafe (which has no first name) is at the top.

Summary

  • Rules about the data - what matches, what order - belong in the model, where every part of the program shares them and Check can test them. Views ask the model what to show.

  • An object parameter with destructuring and defaults, list({ search = '', sort = 'last' } = {}), gives named arguments.

  • Object.entries gives an object's [name, value] pairs; some is true if any item passes a test; ([k, v]) => destructures a pair.

  • Sort with a compare function that compares keys in order and breaks ties; compare texts with localeCompare.

  • F4 is Find and F6 is Sort in the Style Guide. Settings that belong to the application go in app.

Answers

1 Add it to SORTS - category: 'Category' - and a key in compare:

The menu and F6 pick it up by themselves.

2 Give nextSort a direction, and add a case to key: 
case 0x196: this.nextSort(-1); return true;   // Shift-F6
...
nextSort(d = 1) {
  const keys = Object.keys(SORTS);
  const i = keys.indexOf(this.app.prefs.sort);
  const n = keys.length;
  this.setSort(keys[(i + d + n) % n]);
}
(Adding n keeps the number from going below 0.)

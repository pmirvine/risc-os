An address book shouldn't be an island. Other programs - the address books in phones, email programs, spreadsheets - can swap contacts using two common formats, vCard and CSV. In this chapter Contacts learns to read and write both: you'll be able to drop other programs' files on it, save contacts for other programs, and drag contacts straight out of the list. The program is !Contacts8, and the new code is in the toolkit module Formats and a module of Contacts' own, Import.

Two formats

A vCard is the standard way to pass on one person's details; a .vcf file holds one or more of them. Each card is lines of text between BEGIN:VCARD and END:VCARD, each line a property's name, a colon and its value:

BEGIN:VCARD
VERSION:3.0
N:Smith;Ann;;Dr;
FN:Ann Smith
TEL;TYPE=CELL:07700 900123
EMAIL;TYPE=INTERNET:ann.smith@example.com
ADR;TYPE=HOME:;;1 Acorn Road\nCambridge;;;CB1 2AB;
END:VCARD
Some properties have several parts separated by semicolons: N is surname; first name; other names; title; suffix, and ADR has seven parts (post office box; extended address; street; town; county or region; postcode; country). Contacts writes its address into the street part and the postcode into the postcode part; reading, it puts the street, town, region and country together, a line each, as the address. Things after a semicolon in the name (TYPE=CELL) are parameters, saying what kind of telephone number or address it is. A newline in a value is written \n, and a semicolon or comma that is part of a value has a \ in front. Contacts writes version 3.0 and reads 3.0 and the older 2.1, which many programs still write.

CSV (comma-separated values) is simpler: a table as text, a line for each row with the values separated by commas. The first row usually holds the columns' titles:

First name,Surname,Mobile,Email
Ann,Smith,07700 900123,ann.smith@example.com
"Bob, Jr",Jones,,bob@acornpies.example
A value containing a comma, a quote or a newline is put in double quotes, and a quote inside it is written twice. Every spreadsheet reads and writes CSV, which makes it the easy way to get a list of names into and out of other programs.

Characters

There is a snag. Text is stored as numbers, one for each character, and different systems number characters differently. RISC OS 3.71 uses Latin-1: 256 characters, one byte each, enough for English and western European languages (£, é, ß...). Today's programs use Unicode, which has room for every alphabet (and emoji), usually stored as UTF-8: the first 128 characters are one byte each, the same as Latin-1, but everything else takes two to four bytes. So a UTF-8 file read as if it were Latin-1 shows é as two strange characters, and a Latin-1 file read as UTF-8 goes wrong the other way.

Formats has two functions to deal with this:

decode turns the bytes of a file into text. It tries UTF-8 first - TextDecoder with fatal: true gives up with an error if the bytes aren't valid UTF-8 - and if that fails, takes each byte as a Latin-1 character. (catch { with no name in brackets is allowed when the error itself isn't needed. Array.from(bytes, fn) makes an array from something list-like - here the bytes - passing each through fn on the way; String.fromCharCode(b) is the character with code b.) Any character outside Latin-1 becomes a ?, because RISC OS couldn't show it. encode turns text into UTF-8 bytes for the files Contacts writes for other programs, which will expect UTF-8.

Writing vCards

esc puts a \ before backslashes, commas and semicolons and writes newlines as \n. vcardWrite builds each card as an array of lines. The little function add only adds a property if the contact has a value for it, so there are no empty lines.

Lines are joined with \r\n (carriage return and newline), as the vCard standard asks, and a line longer than the standard allows is folded: broken, with a space at the start of the next line. The limit is 75 octets - bytes - as the file is written, and Contacts writes UTF-8, where a character above 127 (such as é) takes two bytes. So fold, which is exported because the organiser's calendar files use the same rule (chapter 16), goes through the line a character at a time with for...of, counting one or two for each, and starts a new line (with its space) before the count would pass 75.

Reading vCards

Reading is the harder half, because other programs write vCards in many small variations.

First the folded lines are joined up again. vCard 2.1's quoted-printable values have line breaks of their own - a line ending in = goes on on the next - so a line ending in = is joined to the next, but only if its parameters say QUOTED-PRINTABLE: other values, such as a picture coded as text, may end in = quite properly, and joining those would swallow the card's END. Then each line is split by a regular expression into the property's name (m[1]), its parameters (m[2]) and its value (m[3]). Some programs put a group name before the property (item1.EMAIL); replace(/^.*\./, '') removes it. Quoted-printable values have bytes written as = and two hex digits (=E9 is é in Latin-1). Those are turned back into bytes, and if the parameters say CHARSET=UTF-8, the bytes are decoded as UTF-8 with decode (Uint8Array.from makes the array of bytes it needs), because in UTF-8 é is two bytes, =C3=A9.

A switch then puts each property's value into the contact being read. c.mobile ??= v (chapter 3) sets it only if it isn't set already: a card may have several mobile numbers, and Contacts keeps the first. const [last, first, , title] = ... is array destructuring, as in chapter 3's dateKey; the empty place between the commas skips the third part.

parts splits a value at its semicolons - but not at \;, a semicolon that is part of the value. That's what (?<!\\) in its regular expression means: "not after a backslash".

At END, a card with no name parts but a full name (FN) uses that as the first name, and the contact is added to the list.

CSV

csvWrite makes the header row from the fields' titles, then a row per contact, quoting the values that need it. csvRows reads a CSV file a character at a time, because a quoted value can contain commas and even newlines, so splitting at every comma or line break would go wrong. It remembers whether it is inside quotes: there, a doubled quote is one quote and a single quote ends the value; outside, a comma ends a value and a newline ends a row. rows.at(-1) is the last row (chapter 3).

csvRead starts with const [header, ...rows] = csvRows(text): destructuring with a rest - ...rows takes everything after the first item as an array of its own, so header is the first row and rows the others. It matches each column to a field by its title, ignoring case, spaces and punctuation, so Surname, surname and SURNAME all find the surname. Columns it doesn't know are left out.

All of these are ordinary functions of text, with nothing to do with windows, so Contacts' Check program tests them: it writes a card and a CSV file and reads them back, reads a vCard 2.1 card and a CSV value with quotes and a comma in it, and decodes UTF-8 text containing a character RISC OS doesn't have.

Files dropped on Contacts

Contacts' own module Import uses Formats to add other programs' contacts to an address book:

importData decodes the bytes, and reads them as vCards if they contain BEGIN:VCARD, otherwise as CSV. importFiles deals with a list of dropped files: a Contacts file is opened as an address book of its own, and anything else is imported.

When files are dropped on a window, the window gets a 'dataload' event listing them, as Doodle did in the first book. Contacts' window also listens for 'datasave', which is what happens when another program's Save box icon is dropped on it - Edit's, say:

Saving for other programs

File > Export has two submenus, vCard and CSV, each a Save box. The Style Guide's rule is that Save saves in the application's own format, and other formats are exported:

It exports the chosen contacts, or, if none is chosen, all the contacts the list is showing - so with something typed in the Find field, only the ones that match. The vCard file is given type Text, as vCard has no RISC OS type of its own, and the CSV file type &DFE, which is CSV's. The names end /vcf and /csv: RISC OS writes a . in a file name as /, so on a computer that uses extensions (or through HostFS) they become Cards.vcf and Contacts.csv, which other programs recognise.

Dragging contacts out

The most RISC OS way to pass contacts on is to drag them: choose some, and drag them from the list to a directory display - or into another program's window. ListView emits a 'drag' event when a drag starts on the chosen rows, and the window passes it on:

dragSave, which the desktop provides, does the rest: it drags a file icon, and when you let go it writes the data into the directory display it's dropped on, or offers it to the program whose window it is. The file is named after the contact (with anything that isn't a letter or digit turned into _, which a file name can hold), or Cards for several.

Trying it

1 Start !Contacts8 and drag Friends onto its icon. Then drag Colleagues from the same directory onto the Friends window: three contacts are added.

2 Choose a contact and drag it to a directory display. A file named after them appears. Shift- double-click it to read the vCard in JsEdit.

3 Choose a few contacts, and use Menu > File > Export > CSV to save them. Open the file in JsEdit, change a name, save it and drop it on a new, empty book from the icon bar.

Summary

  • vCard (a card per person, NAME;PARAMETERS:value lines) and CSV (rows of comma-separated values, with a header row) are how contacts pass between programs.

  • RISC OS 3.71 uses Latin-1; other programs use UTF-8. Decode files with TextDecoder, turning characters RISC OS can't show into ?; encode exported files as UTF-8.

  • Keep file formats in functions of text only, and test them.

  • 'dataload' brings dropped files; 'datasave' and ev.receive() bring data straight from another program.

  • Save in your own format; export others with Save boxes of their own; dragSave lets the user drag data out of a window.

  • x ??= y sets x only if it has no value; const [a, b] = array takes an array apart.

RISC OS programs put the things you do most often where you can reach them with one click: Draw's toolbox, Paint's tools, the button bars of word processors. In this chapter !Contacts gets a toolbar across the top of its window, with buttons for New, Change and Delete, and a Find field that shows only the contacts whose names contain what you type. The toolbar is the fourth toolkit module, Toolbar, which the organiser will use again for its toolbox in Part Two. The result is !Contacts5:

Panes

A toolbar has to stay put while the list scrolls under it, and move when the window moves. RISC OS does this with a pane: a second window, with no title bar or scroll bars of its own, that the Wimp keeps directly in front of the main window and moves with it. Draw's toolbox is a pane, and so is the toolbar of !JsEdit, the editor you may be reading this beside.

The desktop does the work. You make the pane as an ordinary window with flags: { pane: true }, and then attach it to the main window:

win.attachPane(pane, { dx: 0, dy: 0, h: 44, fitWidth: true });
dx and dy say where the pane sits, measured from the top-left of the main window's visible area; fitWidth makes it as wide as the window, whatever size the user drags it to. From then on the pane opens, closes, moves and comes to the front with the window. It covers the top of the window's work area, so whatever is drawn there must start lower down - you'll see how the list does that in a moment.

Pictures of the program's own

The buttons need pictures. A RISC OS program usually keeps its sprites in a sprite file in its application directory, and !Contacts5 has two: !Sprites, with the application's icon, which !Run puts in the Wimp's sprite pool with IconSprites so the Filer and the icon bar can show it (as the first book's !Snake did), and Sprites, with the toolbar's pictures tb_new, tb_edit and tb_delete. Double-click Sprites to look at them in Paint - and to draw your own.

The toolbar's pictures don't go into the Wimp's pool. The pool is shared by every program on the desktop, so a name like tb_new could easily clash with another program's. Instead the program reads the file into a sprite area of its own, which is what !RunImage now does before anything else:

sprites.spritesFromFile turns the bytes of a sprite file into a sprite area. ctx.dir is the application's directory (the first book's chapter 12), so the file is found wherever the application is copied. Reading the file takes time, so start is now an async function and awaits it.

The Toolbar gives the area to its pane (spriteArea: area): an icon in the pane looks for its sprite there first, and only then in the Wimp's pool.

Passing the application around

Look at the last lines of start: MainWindow is now given app, not task. app is a small object holding what belongs to the whole application rather than to one window: the task, and now the sprite area.

Why not just add the area as a third argument, new MainWindow(task, book, area)? Because the list would keep growing: chapter 6 adds the user's sort order, and later chapters add more. Every new thing would change the constructor, and every call of it. With one app object, new things go into app and the constructor stays the same. MainWindow keeps this.task = app.task, so the rest of its code doesn't change.

Help for each button

Buttons with only pictures need explaining, and the Toolbar lets each one carry interactive help, shown by !Help when the pointer is over it:

{ name: 'new', sprite: 'tb_new', action: () => this.add(),
  help: 'Click SELECT to add a contact.' },
!Contacts5 leaves it out to keep the listing short; chapter 9 gives help to every button, menu entry and window in the program.

A Find field

The toolbar also has a writable icon labelled Find, made by the search option. Whenever its text changes - every key you type - the Toolbar calls the change function MainWindow gave it, which keeps the text and refreshes the list:

refresh now shows only the contacts whose names contain the Find text. toLowerCase on both sides means capitals don't matter: smi finds Smith. With the Find field empty, every name contains the empty string, so every contact is shown. Escape in the Find field clears it, and Return gives the keyboard back to the list.

This first version only looks at names, and it does the looking in the window. In the next chapter that turns out to be the wrong place.

Trying it

1 Run !Contacts5. The Change and Delete buttons are greyed out: nothing is selected.

2 Click a contact: they come to life. Press Ctrl-A: Change goes grey again (more than one is selected), Delete doesn't.

3 Click in the Find field and type ev: only Evans, Carol is left. Press Escape to see everyone again.

4 Drag the window by its title bar and resize it: the toolbar goes with it.

Summary

  • A pane is a window the Wimp keeps in front of another and moves with it. Make it with flags: { pane: true } and attach it with win.attachPane(pane, { ... }).

  • The Toolbar module makes a pane of buttons from a list; the program gives it the actions, and greys buttons out with shade.

  • A program's own pictures belong in a sprite area of its own, read from its sprite file with sprites.spritesFromFile, so their names can't clash with other programs'.

  • Pass one app object holding the application's shared things, rather than a growing list of arguments.

  • Buttons are always visible, so shade them when the selection changes (the ListView's 'select' event); menus can work it out as they open.

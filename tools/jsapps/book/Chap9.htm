Contacts now does everything an address book must. This chapter adds what makes an application pleasant to use and a good citizen of the desktop: undo, choices that are remembered, interactive help, information about a file, and taking care of your work when the desktop shuts down. At the end is the finished !Contacts, and a checklist of what a well-behaved RISC OS application does.

Undo

Everybody deletes the wrong thing sometimes. An application that can undo it makes people confident enough to try things. The Style Guide gives undo and redo the keys F8 and F9.

The idea is to describe each change as an object that knows how to make the change and how to take it back: a command. An object with do and undo methods, and a name to show in the menu:

{ name: 'Delete',
  do: () => book.remove(bob.id),
  undo: () => book.put(bob) }
Instead of changing the book directly, the program gives the command to an Undo object, which carries it out and remembers it. The last toolkit module for Part One keeps two stacks - the changes that can be undone, and the ones that have been undone and could be redone:

do carries out a command and pushes it onto done. undo pops the last one, takes it back, and pushes it onto undone; redo does the reverse. Making a new change empties undone: once you've done something new, redoing the old change would make no sense. Only the last 50 changes are kept, so memory isn't filled up. at(-1) is the last item (chapter 3), and each change of state emits 'change', so the menus and toolbar can follow.

Each document has its own Undo (this.undo = new Undo() in the Document constructor), so undoing in one address book never touches another.

Choices

Most applications let you change how they behave, and remember your choices. The Style Guide says how:

  • A Choices... item on the icon bar menu opens a dialogue box.

  • The box has four buttons: Default puts the standard settings in the box, Cancel closes it, Set uses the settings now, and Save uses them and keeps them for next time.

  • Choices are saved in the Choices directory, not beside the application: the application may be on a disc you can't write to, or shared by several people.

The desktop provides choices.read(name, defaults) and choices.write(name, value), which keep a JSON file called name in the Choices directory (Choices:Contacts). read returns the defaults for anything not saved yet. Contacts' module Choices uses them:

Interactive help

RISC OS's !Help application (in the Apps icon's directory) shows a line or two about whatever is under the pointer. For it to work in your application, every window, icon and menu item should have help text. It is easy to add, and makes an application much easier to learn.

A window
help in its description: the text shown anywhere in the window without help of its own.

An icon
help in the icon's description. The toolbar passes each button's help on to its icon:

A menu item
help in the item: { text: 'Save', ..., help: 'Save the book.' }.

The icon bar icon
help in addIconbarIcon.

Help text is short, and says what clicking does, in the Style Guide's words: Click SELECT to.... |M in help text starts a new line.

The Form module passes each field's help on to its icons the same way, so dialogue boxes can have help too - the Choices box does.

When the desktop shuts down

When you choose Shutdown from the Task Manager, the desktop sends every task a PreQuit message first, asking whether it minds. An application with unsaved work should object, and ask:

msg.object() stops the shutdown. If you then choose to discard the changes, Contacts quits, and starts the shutdown again (with the key Ctrl-Shift-F12, as RISC OS applications do) - unless the message was only for Contacts (msg.single: the Task Manager's Quit on this one task).

A Style Guide checklist

Contacts now does what Acorn's RISC OS Style Guide asks of an application that edits documents:

  • An icon on the icon bar: Select opens a new document; Menu gives Info, Choices... and Quit; files dropped on it are loaded.

  • Documents of its own file type, with an icon, opened by double-clicking - in the copy already running.

  • The file's name in the title, with * while it has unsaved changes.

  • Save with F3 and a Save box; other formats exported with Save boxes of their own.

  • Discard/Cancel/Save before closing a changed document, and at shutdown.

  • A toolbar of 3D buttons, shaded when they can't be used, repeating what's in the menus.

  • Menus built from the current state: items shaded or ticked, shortcut keys shown.

  • The standard keys: F3, F4, F6, F8, F9, Ctrl-A, Insert, Delete.

  • Dialogue boxes with the default action on the right, Return for it and Escape for Cancel.

  • Drag and drop both ways: files in, data from other programs in, contacts out.

  • Choices with Default, Cancel, Set and Save, kept in Choices.

  • Interactive help everywhere, and a !Help file.

Summary

  • Undo: describe each change as a command with do and undo; an Undo object carries them out and keeps stacks of done and undone commands. Give each document its own.

  • A menu item's text can be a function, worked out each time the menu opens.

  • Choices: a Choices... box with Default, Cancel, Set and Save, saved with choices.write in the Choices directory and read with choices.read.

  • Interactive help: help on windows, icons, menu items and the icon bar icon; |M for a new line.

  • File > Info shows the document's details; PreQuit lets you protect unsaved work at shutdown.

Exercises

1 Make the number of changes kept for undo a choice, from 10 to 200.

2 Add a choice for whether the email column is shown.

3 Give the list's column headings interactive help: Click SELECT to sort by this column - and make clicking a heading sort by it. (The list's ListView draws the headings in the top 20 pixels below the toolbar.)

4 Undo remembers changes after saving. Some programs clear it when the document is saved; others mark the point, so undoing past it puts the * back. Which do you prefer? Make Contacts put the * back correctly.

Answers

1 Add undoLimit: 50 to DEFAULTS, a field for it in the Choices box (with allowed: '0-9'), and in Document: this.undo = new Undo(app.prefs.undoLimit). Check the number in the form's check function: 
check: (v) => (+v.undoLimit < 10 || +v.undoLimit > 200
  ? { field: 'undoLimit', message: 'From 10 to 200, please' }
  : null),
Two more things are needed. openChoices copies only sort and confirm from the box into prefs, so it must copy the new one too; and a writable field's value is a string, so turn it into a number as it's copied: 
Object.assign(prefs, { sort, confirm: r.values.confirm,
  undoLimit: +r.values.undoLimit });
(A document already open keeps the limit it was made with.)

2 Add email: true to DEFAULTS and an option field, and build the columns from the choices, then call setItems again when they change (or make a new ListView).

3 The list takes every click on its window - including a click on the headings, which it ignores - and a handler that returns true stops the ones added after it. So add a 'click' handler to the window in MainWindow's constructor before the ListView is made. The headings stay at the top of the visible area as the list scrolls, so a click is on them when ev.y is between w.scrollY + this.bar.height and 20 more. Add up the columns' widths to find which one holds ev.x; only Name has an order to sort by (setSort('last')), unless you add more to SORTS. Return true when the click was on the headings, and nothing otherwise so the list gets it. The help goes in a 'helprequest' handler on the window, setting ev.text when the pointer is over the headings, tested the same way.

4 Remember which command was last done when the document was saved, and compare after each undo or redo: 
// in save:
this.savedAt = this.undo.done.at(-1);
// in the Document constructor:
this.undo.on('change', () =>
  this.setModified(this.undo.done.at(-1) !== this.savedAt));
(The book's 'change' handler still sets modified when a change is made; this corrects it after undo and redo.)

An organiser is mostly about days, so this chapter is about dates: why JavaScript's own dates are awkward, a small module that makes them easy, and the diary's four ways of looking at time - a week, a day, a month and a year. It also gives the binder a toolbox down its left-hand side, as Lotus Organizer had. The program is !Org11.

JavaScript's dates

JavaScript has a Date object, and you met it in the first book's Clock. A Date is a moment in time - a particular millisecond - and it can tell you the year, month, day and hour of that moment:

const d = new Date(2026, 8, 25, 12);   // 25 September 2026, noon
d.getFullYear()    // 2026
d.getMonth()       // 8 - September!
d.getDate()        // 25
d.getDay()         // 5 - Friday (Sunday is 0)
Three things about it catch everyone out.

Months count from 0
new Date(2026, 8, 25) is in September, not August: January is month 0. Days of the month count from 1 as usual, and getDay counts the days of the week from Sunday, 0.

It's a moment, not a day
An appointment is on a day, but a Date is an exact moment, which falls on different days in different places. Store "25 September" as a Date and it can come back as the 24th on a computer set to another time zone.

Summer time
Twice a year the clocks change, and a day is 23 or 25 hours long. Add 24 hours to midnight on the day the clocks go back and you land at 11 at night on the same day, not the next day.

The organiser avoids all three by hardly using Date at all. A day is written as a key, a string like '2026-09-25': year, month (from 1!) and day, always with two digits for the month and day. Keys have two lovely properties: comparing them as text compares them as dates ('2026-09-25' < '2026-10-01' is true), and they go into files, and into Maps, exactly as they are. Only one module, Dates, turns keys into Dates, and it always makes them at midday - far enough from midnight that no clock change can move them to another day.

The Dates module, tests first

Date arithmetic is easy to get nearly right, and the mistakes show up months later ("why is my appointment on the wrong day in March?"). So this module was written tests first: before writing addMonths, write down what it should do, including the awkward cases, in Check:

Each line is a question with its answer worked out by hand: three days after 29 September is 2 October; a month after 31 January is 28 February, because there is no 31 February; a year after 29 February 2024 is 28 February 2025; 25 September 2026 is a Friday (4, because the module counts the week from Monday, 0); its week starts on Monday the 21st; the Christmas to New Year gap is 7 days; the calendar for September 2026 starts on Monday 31 August. Run Check before the module exists and every test fails; write the module until they all pass; and whenever you change it later, run it again to see that nothing broke.

Check itself has one new trick. Two objects with the same fields in a different order are the same entry, but JSON.stringify writes them differently. So check gives stringify a second argument, a replacer function it calls for every value it writes:

For an object (not an array), the replacer returns a copy with its fields in alphabetical order: Object.entries makes it a list of [name, value] pairs, sort sorts them by name, and Object.fromEntries turns the pairs back into an object.

Converting between keys and Dates is the only place months are adjusted by one:

dateOf uses array destructuring (chapter 3) on key.split('-').map(Number), which turns '2026-09-25' into [2026, 9, 25], and makes the Date at 12 o'clock.

Adding days lets Date do the hard part:

setDate accepts days beyond the end of the month and carries them over: setting 29 September's day to 32 gives 2 October. addMonths can't simply do the same with months, because 31 January plus one month would carry over to 3 March; so it finds the first of the new month, then chooses the day, no later than the month's last. daysInMonth uses the same carrying the other way: day 0 of a month is the last day of the month before, so new Date(year, month, 0) - with month counted from 1, which Date takes as the next month - is the last day of the month we want.

Subtracting two Dates gives the milliseconds between them, and a day is 86,400,000 milliseconds; Math.round absorbs the extra or missing hour of a clock change. weekday turns Date's Sunday-first count into a Monday-first one - (day + 6) % 7 - because in Britain, as in the organiser, the week starts on Monday.

A calendar page needs every day it shows, in weeks, including the ends of the months before and after:

Six weeks is always enough: a month of 31 days that starts on a Sunday spans six rows.

Reading dates and times typed into the dialogue boxes is done here too, so every part of the organiser accepts the same forms:

parseDay tries 25/12/2026 first and, if that fails, 2026-12-25. The second try is inside the condition, as (m = /.../.exec(s)): an assignment is also an expression, whose value is what was assigned, so the condition is true if the second pattern matched. Either way it ends with the year, month and day, checks them - there is no 31 February - and returns a key, or null.

format hands the desktop's formatTime (appendix C) a Date made from the key, so D.format(key, '%WE %ZDY %MO') is Friday 25 September.

The diary

An appointment is an entry with a date (a key), a time ('09:30', or '' for all day), an end time and what it is. The diary's Collection gains one method, to find the appointments in a range of days:

It asks datesOf which days in the range each appointment falls on, and sorts the lot by date and time together - both are strings that sort correctly, so joining them sorts by date first, then time. For now an appointment falls on just its own date; in the next chapter appointments can repeat, and only datesOf will change.

The Diary section replaces the first blank in the list of sections:

Its views are Week, Day, Month and Year; this.day is the day being looked at, and every view shows the page that contains it. While drawing, a view records each day's rectangle with dayBox, as it records entries with box, so dayAt can say which day is at a point. itemsOn collects what to show on a day - for now its appointments; later, to-dos, anniversaries and planner bars will join them - as small objects with a kind, a time, a text and a ref.

draw is one line: V[this.view.toLowerCase()](this, g, L, R). At the top of the file, import * as V from './DiaryViews' imports everything the module DiaryViews exports, as the properties of one object, V. Its four drawing functions are V.week, V.day, V.month and V.year, so V['week'] is the week function: the view's name chooses the function. (import * as D from './Toolkit/Dates', at the top of every module that uses dates, works the same way, and makes calls such as D.addDays easy to spot.)

Four ways to see the time

All four views are in DiaryViews:

The week view is the diary's everyday view, as it was in Lotus Organizer: Monday to Wednesday on the left page, Thursday to Sunday on the right, each day a box with its appointments in time order.

dayCell draws one day: its date, red if it's today, shaded if it's the chosen day, then as many entries as fit, with ... if some don't. week finds the Monday of the chosen day's week and draws seven days from it.

The month view shows this month on the left and the next on the right, as calendars:

monthGrid gives the days; days that belong to the months before and after are shown faintly, aren't recorded with dayBox, and show no entries. Each day shows as many of its entries as its box has room for, in a small size, and +2 if two more didn't fit.

The year view is six small months on each page, with days that have entries in bold blue, so you can see at a glance where the busy weeks are. Clicking a day in the month or year view goes to that day's week. The day view shows two days, by the hour from 8:00 to 20:00, with anything without a time at the top.

Getting about

The page corners, and Page Up and Page Down, turn the diary's pages. How far depends on the view:

turn is a chain of conditional operators, one view per line: a week at a time in the week view, two days in the day view (the two pages), two months in the month view and a year in the year view.

In the week view the arrow keys move the chosen day: left and right a day, up and down a week. The step comes from an object used as a table: { 0x18C: -1, 0x18D: 1, 0x18F: -7, 0x18E: 7 }[ev.code] looks up the key's code in it, giving the number of days, or undefined for any other key. Home goes back to today: the window's key method calls section.today() for it (the Address section's today does nothing), and the window's menu gains View, listing the section's views, and Today.

What the buttons are and do is in a module of its own, Tools, which will grow in the next few chapters:

The first button shows today's date and goes to it. The rest are for the views - but each section has different views (the Diary has four, the Address section none), so there are four spare buttons, which updateToolbox relabels, hides and selects to match the section. The spread ... puts the four into the list of buttons.

Summary

  • Date counts months from 0 and is a moment, not a day; clock changes and time zones can move it to another day.

  • Keep days as keys, '2026-09-25': they sort and compare as text and save as they are. Keep Date inside one module, at midday.

  • Write tests first for fiddly code: the awkward cases (month ends, leap years) become part of the program.

  • JSON.stringify(value, replacer) lets a function change what is written; Object.fromEntries makes an object from [name, value] pairs.

  • import * as X from './Module' imports all a module's exports as one object; X[name] chooses one by name.

  • An object can be a lookup table: { a: 1, b: 2 }[key].

  • Array.from({ length: n }, (_, i) => ...) makes an array of n items.

  • The Toolbar makes a Draw-style toolbox with side: 'left'; buttons can be relabelled, hidden and selected as the program's state changes.

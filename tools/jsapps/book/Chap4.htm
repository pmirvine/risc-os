In chapter 3 every change to the address book was followed by a call to refresh, so that the list showed it. That works while there are two changes, but an application soon has many ways to change its data - menus, keys, buttons, files dropped on it - and sooner or later one of them forgets. In this chapter the book tells the window when it changes, so the window can never be out of date. You'll also add the rest of the things a user expects of a list: a Delete key that asks first, Select all, and a menu whose entries are greyed out when they can't be used. The result is !Contacts4.

One source of truth

There are now two copies of the contacts in the program: the Book, which holds them, and the list in the window, which shows them. The Book is the one that matters - it's what will be saved in chapter 7 - so it is called the source of truth. The list is only a picture of it.

A picture can be out of date. Look at chapter 3's add and edit: each changed the Book and then called this.refresh(). If some later piece of code changed the Book and didn't call refresh, the window would go on showing the old contacts until something else happened to redraw it - the kind of mistake that is easy to make and hard to find.

The answer is to turn it round. Instead of every piece of code that changes the Book remembering to tell the window, the Book tells anyone who is interested, every time it changes. That's what the Emitter it is built on (chapter 1) is for: the Book already emits a 'change' event from add and update. All the window has to do is listen.

Asking before deleting

Deleting is the one thing the user can't take back (until chapter 9 adds Undo), so the Style Guide asks programs to check first. remove in MainWindow does that:

query is the desktop's query box, the one Edit uses to ask "Discard changes?". You give it a message and the names of its buttons; it gives back a Promise that resolves to the text of the button that was clicked (or null if the box was closed), so await waits for the answer, just as await editCard(...) waits for the card.

The message is made with the conditional operator:

const what = gone.length === 1 ? nameOf(gone[0])
  : `these ${gone.length} contacts`;
a ? b : c is a short if that gives a value: if a is true it is b, otherwise c. So one contact is named ("Delete Evans, Carol?") and several are counted ("Delete these 3 contacts?"). The button is labelled Delete rather than Yes: the Style Guide asks for buttons named after what they do.

Notice this.focus() after the question, whatever the answer. The query box took the input focus; giving it back to the list means the arrow keys work again straight away.

Keys

A list should work from the keyboard as well as the mouse. The ListView already moves the selection with the arrow keys, Home, Copy and Page Up/Down, and opens the current contact on Return. MainWindow adds the keys that change things, following the Style Guide:

Insert
a new contact (the Style Guide says named keys should do what they say).

Delete (or Backspace)
delete the selected contacts, after asking.

Ctrl-A
select all.

Ctrl-Z
clear the selection. Ctrl and a letter give the codes 1 (A) to 26 (Z).

switch is a neater way of writing a row of ifs that all compare one value. JavaScript compares ev.code with each case in turn and runs the code after the first that matches; case 127: case 8: lets two values share the same code. Each case ends with return, so it goes no further. default catches everything else: it returns nothing, so, as in book 1, the key goes on to other programs (F12 still works, for instance). The ListView's key handling in chapter 2 is a switch too.

The input focus

Keys only go to the window that has the input focus: the one whose title bar is cream. Clicking a row gives the list the focus (the ListView calls wimp.setCaret(this.win) when you click), and MainWindow's focus gives it back after a dialogue box. If the keys seem to do nothing, click in the list first.

As in book 1, the menu is made each time it opens, so it always shows how things are. The difference is that shaded is given a function rather than true or false. The menu calls it when it's drawn, so Change is greyed out unless exactly one contact is selected, and Delete and Clear selection unless at least one is. none is a small function kept in a variable because two entries use it.

key: '^A' writes the key at the right of the entry. It only shows the key: the key itself is handled by key(ev). The Style Guide writes Ctrl as ^ and Shift as an arrow.

Summary

  • Keep the data in one place, the model, and let it tell the views when it changes (book.on('change', ...)). Code that changes the data never has to update the windows.

  • The ListView keeps its selection by key, so it survives the list being refreshed.

  • query asks a question with buttons and resolves to the button clicked. Ask before deleting, and name the button after the action.

  • a ? b : c is b if a is true, else c. switch picks code by comparing one value with several cases.

  • The Style Guide's keys: Insert, Delete, Ctrl-A select all, Ctrl-Z clear selection. Keys go to the window with the input focus.

  • Menu entries can be shaded by a function, worked out as the menu is drawn; key shows the entry's key.

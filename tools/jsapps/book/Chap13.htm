Lotus Organizer's To Do section was a list of the things you had to do, with the most urgent at the top, each with a little numbered square for its priority, crossed through when it was done. In this chapter your organiser gets one. It's a smaller step than chapter 12's: a new kind of entry, a new page to draw it on and a form to change it with - three things you have done before. What is new is that the section doesn't live on its own: a thing due on a day also appears in the Diary on that day, and dragging it to another day there changes when it is due. The result is !Org13.

Planning the To do section

As in chapter 1, start with what the section remembers and what can happen to it.

What it remembers
For each thing to do: what it is (the text), a priority from 1 (the most urgent) to 3, the day it can be started and the day it is due (either may be left out), a category, and whether it has been done.

What can happen
Things are added (the New button), changed (double-click), ticked off and unticked (click the box), deleted (the Delete key or the wastebasket, from chapter 12), shown all or only those not yet done, and shown in the Diary on the day they are due - where dragging one to another day moves its due date.

That is enough to write the model. An entry looks like this:

{ id: 4, text: 'Renew the car insurance', priority: 1,
  start: '', due: '2026-09-28', category: 'Home', done: false }
The dates are day keys, 'YYYY-MM-DD', from chapter 11's Dates module, so they can be compared and sorted as plain strings.

The ToDo collection

Every section's entries are kept in a Collection (chapter 10): a Map from id to entry that emits 'change' whenever it changes. The Diary's collection added occurrences; the To do section's adds the two questions the rest of the program will ask it:

dueOn is for the Diary: the things due on a day that aren't done yet. list gives the order the page shows them in.

Sorting on three things

The compare function in list sorts by three things in turn, joined with ||: first those not done, then by priority, then by due date. Each part is a number that is 0 when the two entries are equal on that point, and because 0 counts as false, || goes on to the next part only then. (Chapter 6's list did the same with a loop over the sort keys; with a fixed three, || is shorter.)

The first part takes one true-or-false from another: a.done - b.done. When JavaScript does arithmetic with true and false it treats them as 1 and 0, so the result is -1 when only b is done (a comes first), 1 when only a is, and 0 when they are the same.

The last part compares due dates with localeCompare. A thing with no due date has '', which would sort first; (a.due || '9') puts '9' in its place, and since every day key starts with a '2' (or '1'), '9' sorts after all of them: things with no date go to the bottom of their priority.

Drawing the list

The page's draw fills the left page and then carries on on the right, a row of 24 pixels each:

per is how many rows fit on a page; the first per things go on the left and the next per on the right (i % per is the row on its page). The heading on the left counts what's left to do - filter keeps those not done and length counts them.

Each row is drawn by row:

From left to right: the priority in a coloured square, the box to tick, the text, and the due date at the right-hand end.

  • The square's colour comes from an array indexed by the priority: red, orange and green for 1, 2 and 3. If an entry somehow had another priority, [...][t.priority - 1] would be undefined, and ?? gives grey instead. The square has the number in it as well, so the priority can be read without the colour.

  • A thing that's done has a tick in its box, its text in the faint colour, and a line through it: a rectangle one pixel high across the middle of the text, as wide as the text (measureText) but no wider than its column.

  • late is true for a thing not done whose due date is before today. Comparing day keys as strings is enough: '2026-09-22' < '2026-09-25'.

The row remembers two places. this.ticks gets the tick box's rectangle, for the click that ticks it; and this.box(...) - chapter 10's record of where each entry is drawn - gets the rest of the row, so that choosing, double-clicking, deleting and dragging all work as they do in the Diary.

Colour never alone

An overdue thing is drawn in red. That's a good signal for most people, but the Style Guide says colour must never be the only difference between things: a user who can't tell red from black, or has a monochrome screen, would miss it. So an overdue date has a ! in front of it and is in bold as well:

const due = (late ? '! ' : '') + showDay(t.due);
The same goes for the priorities (the number is in the square) and for done things (they are ticked and crossed through, not just faint). You'll meet the rule again in chapter 15's planner.

Ticking and changing

A click on a tick box turns done round:

By the time the page sees the click, the window has already dealt with choosing: it gives every click to tools.clickEntry first (chapter 12), which chooses the entry under the pointer, and then passes the click on to the section. So clicking a tick box both chooses the row and ticks it. click returns true if it used the click and false if it wasn't on a tick box, as every section's click does, but the window doesn't need the answer. Notice that the page doesn't redraw itself: it changes the collection, the collection emits 'change', and the window, which listens to every part of the document, redraws - the same "one source of truth" as chapter 4.

Double-click a thing to change it, or double-click an empty row (or click the New button) to add one:

The form is made by editToDo, next to the Diary's forms in Entries:

It is chapter 3's Form again, with three kinds of field you've seen before: lines: 2 for a text of two lines and choices for a pop-up menu of the three priorities, both from !Contacts' card, and option for the Done switch, from the Choices box (chapter 9).

The form shows things differently from how the model keeps them, so editToDo translates both ways. Going in, the day keys become 25/09/2026 (showDay) and the priority number becomes one of the menu's texts; coming out, D.parseDay turns the dates back into day keys, and PRIORITIES.indexOf(v.priority) + 1 turns the text back into a number (|| 2 in case it isn't one of them). The check function refuses a thing with no text, or a date parseDay can't read, and puts the caret in that field - chapter 3's validation.

Two views: All and Undone

A long list of ticked-off things gets in the way, so the section has two views, given to the Section constructor:

Chapter 11's toolbox shows a section's views as buttons down the left, so the To do section gets All and Undone buttons without any more code: clicking one sets this.view, and draw asks the collection for list(this.view === 'All') - everything, or only what isn't done. The window's View menu offers them too.

When the window shows a To do entry from somewhere else - following a link in chapter 14, or a to-do double-clicked in the Diary - the section's go switches to All, so the entry is sure to be on the page:

describe and remove are chapter 12's: a line about an entry (for the "Delete ...?" question) and deleting it (for the Delete key and the wastebasket).

To-dos in the Diary

Lotus Organizer's best trick was that its sections fed each other: a birthday entered in the Anniversary section turned up in the Diary, without being written twice. Chapter 12 did that for anniversaries; now the Diary asks the To do section what is due each day too:

itemsOn gathers everything to show on a day into one list of { kind, text, ref } objects: anniversaries first, then the things due that day, then the appointments. The three ... spread each section's answers into the one array. Every view - week, day, month - draws a day by asking itemsOn and drawing what it gives, so all of them show the to-dos at once.

A to-do in the Diary is drawn with an empty box in front of it, like the one on the To do page:

Each item's ref says whose entry it is: { section: 'todo', id }. That's all the rest of the organiser needs. Double-click a to-do in the Diary and chapter 12's double sees that the entry isn't the Diary's own and goes to it in the To do section instead:

if (box?.ref.section === 'diary') return this.edit(box.ref);
if (box) return this.org.go(box.ref);        // someone else's
Drag one into the wastebasket and Tools.remove finds the section named in the ref and asks it to describe and remove the entry. The Diary doesn't need to know anything about to-dos beyond how to draw them.

The section is put into the binder where chapter 10 left a blank page for it:

Dropping a to-do on a day

Chapter 12 let you drag an appointment to another day. Dragging a to-do works the same way, because the Diary's dropped looks at whose entry has been dropped:

For a to-do, moving it to a day means that's when it is due, so dropped just updates its due. The collection emits its change, the window redraws, and the to-do appears on its new day - and moves on the To do page too, since the list is sorted by due date.

Trying it

1 Double-click !Org13 in $.Examples.JSApps, then double-click the sample organiser, Diary, in the same directory: the running !Org13 opens it (so would dragging it to !Org13's icon bar icon).

2 Click the To do tab. Things overdue have a red date with a !; Water the plants is done, so it is ticked, crossed through and at the bottom.

3 Click the box by Fix the garden gate to tick it off, and click Undone in the toolbox: it disappears from the list. Click All to bring it back.

4 Click the New button and add a thing due tomorrow, with priority 1. It joins the other priority 1 things at the top, in order of their due dates.

5 Click the Diary tab. Your new thing is on tomorrow, with an empty box. Drag it to the day after: then look at the To do page again, where its due date has changed.

Summary

  • Plan a section by what it remembers and what can happen to it, then write its collection and test it in Check before drawing anything.

  • Sort on several things by joining comparisons with ||. true and false count as 1 and 0 in arithmetic, so a.done - b.done puts things not done first.

  • Never show a difference by colour alone: overdue dates have a ! and are bold as well as red.

  • A form can show values differently from how the model keeps them; translate both ways around ask.

  • A section's views become toolbox buttons and a View menu by themselves.

  • Sections feed each other through refs: { section, id } is all another section needs to draw, open, move or delete an entry that isn't its own.

Exercises

1 Show how many things are overdue in the right-hand page's heading, next to the date (for example 2 overdue).

2 Add a third view, Today, showing only things due today or overdue.

3 In the Diary, a to-do is drawn with an empty box. Let a click on that box tick the thing off, straight from the Diary.

4 The start date isn't used yet. Make the To do page leave out things whose start date hasn't come, unless the view is All.

Answers

1 Count them in draw and add the count to the heading's date: 
const late = list.filter((t) => !t.done && t.due &&
  t.due < D.today()).length;
const date = showDay(D.today());
heading(g, R, 'To do', this.colour,
  late ? `${date}, ${late} overdue` : date);
2 Add 'Today' to views, and in draw: 
let list = this.doc.todo.list(this.view === 'All');
if (this.view === 'Today') {
  list = list.filter((t) => t.due && t.due <= D.today());
}
The toolbox shows the third button by itself.

3 In DiaryPage.click, before looking for a day: 
const box = this.at(ev.x, ev.y);
if (box?.ref.section === 'todo' && ev.x < box.x + 12) {
  this.doc.todo.update(box.ref.id, { done: true });
  return true;
}
(The thing then leaves the Diary, since dueOn only gives things not done.)

4 In draw, after getting the list: 
const now = D.today();
const shown = this.view === 'All' ? list
  : list.filter((t) => !t.start || t.start <= now);
and draw shown instead of list. A better place for the rule is the model, as a second argument to list - chapter 6's lesson again.

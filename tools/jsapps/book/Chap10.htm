Part Two builds a much bigger application: a personal organiser, with a diary, a list of things to do, an address book, a notepad, a year planner and anniversaries, all kept in one file. In this chapter you'll plan it, draw its ring binder, work out how its six sections share the binder, and bring the address book across from !Contacts without changing a line of it. The program is !Org10.

A binder on the screen

In the early 1990s, many people carried their lives in a ring binder: a Filofax, with a diary section, an address section and pages for notes, each behind a coloured tab. In 1992 a small British company, Threadz, turned that binder into a program. Lotus bought it and sold it as Lotus Organizer, and for most of the 1990s it was the best-selling organiser there was.

Its window looked like a binder open on the desk: two pages side by side with the rings between them, coloured section tabs down the right-hand edge, and turned-up corners at the bottom of the pages that you clicked to turn over. Down the left was a toolbox, with a button for a new entry, today's date, and a wastebasket you dragged entries into to throw them away. People liked it because it looked and behaved like the paper binder they already knew: everything was always in the same place.

!Organiser borrows those ideas, but it is a RISC OS application. The window's frame, its menus and its dialogue boxes are the Wimp's, as the Style Guide asks; the binder is drawn inside the work area, where an application may draw what it likes, just as Draw draws a drawing.

Planning the organiser

As in chapter 1, start with what it remembers and what happens.

What it remembers. Six kinds of entry, one for each section:

Diary        appointments: a date, a time, what it is,
             perhaps an alarm, perhaps repeating
To do        things to do: a priority, dates, done or not
Address      contacts, exactly as !Contacts keeps them
Notepad      pages of notes, each with a title
Planner      coloured bars across days: holidays, projects
Anniversary  birthdays and other yearly days
and one more list, of links between entries (a meeting and the person you're meeting), which comes in chapter 14. It all goes in one file: open your organiser and everything is there.

What happens.

open a section by its tab; turn its pages
see the diary a week, a day, a month or a year at a time
add, change, move and delete entries
drag entries into the wastebasket
link entries together, and follow the links
be reminded of appointments; print pages
swap appointments with other programs
The chapters take those in turn. This one draws the binder, makes the sections, and does the whole of the Address section, because we already have an address book.

The binder

The binder is a toolkit module, Binder, because it only draws and measures: it doesn't know what the sections are for. Its header comment says how it's used:

The constructor works out where everything goes, once, from the size it's given:

From the outside in: a leather edge (EDGE) all round, a strip down the right for the tabs (TAB), and the rings (RINGS) between the pages. What's left is shared equally by the two pages, which are kept as rectangles, left and right. Every section draws into those rectangles, so no section needs to know how big the window is. The tabs share the height of the page between them (but aren't more than 52 pixels tall), so six fit - and so would seven.

draw paints it in the order you would build it: the cover, the tabs that are behind the pages, the pages, then the open section's tab in front of them (a little wider, so it seems to come out of the binder), the rings and the corners:

The rings are ellipses: g.ellipse(x, y, rx, ry, rotation, start, end) is the canvas's oval-drawing cousin of arc, with two radii instead of one. Each ring is a grey oval with a thinner, lighter one just above it for the shine.

The other half of the module says what is at a point, so the program can tell a click on a tab from a click on a page:

findIndex tries each tab's rectangle. A page corner is a triangle, not a rectangle: a point is inside the bottom-left triangle when its distance in from the left edge plus its distance up from the bottom is less than the corner's size. hit returns a small object describing what's there - { tab: 2 }, { corner: -1 } - and deciding what that means is left to the program.

Sections

The six sections are different, but the window does the same things with each of them: it asks the open one to draw its pages, and passes it the clicks and keys the binder doesn't use. That is the section interface, and Paper writes it down, as a base class every section extends:

The list in the comment is every question the window may ask a section; the ones marked with a chapter number are asked from that chapter on, and this stage's sections don't need them yet. The class answers all of them by doing nothing: draw() {}, click() { return false; } and so on. So a section only writes the methods it needs, and the window can call any of them on any section without checking first. You'll see the list fill up over the next few chapters, as sections learn to add, move and delete entries.

The one thing every section does do is remember where it drew its entries. While drawing, it calls box(x, y, w, h, ref) for each one, where ref is a small object saying which entry it is; afterwards, at(x, y) finds the entry at a point. findLast is find starting from the end: the entry drawn last is on top, so it's the one you clicked. The ref gets the section's id added to it, so it says where the entry lives as well as which one it is: { section: 'address', id: 7 }. That will matter when entries are dragged between sections and linked.

Paper also has some drawing helpers every section uses: heading for a page's title with a line in the section's colour, text for text cut off at a width, and ruled for lines across a page.

Sections still to be written

In this chapter only the Address section is real, but all six tabs should be there. The others are made by a function that makes a class:

blank is an arrow function that returns a class expression: class extends Section { ... } without a name, written where a value is expected, just as a function can be. Classes are values in JavaScript - you can pass them around, keep them in arrays and return them. Each call of blank makes a new class; its constructor and draw can use id, name and colour because they are inside blank, whose parameters they are. The window makes its sections from a list of classes:

map((S) => new S(this)) makes one object of each class, passing the window. In each later chapter a line of that list changes: blank('diary', 'Diary', '#6fa8dc') becomes DiaryPage, and so on, until there are no blanks left.

The window is 900 by 540 pixels, with the binder filling its work area:

The address section: !Contacts again

The Address section is a whole address book, and we have one: !Contacts' Book class (chapters 1 to 9) keeps contacts, sorts and searches them, and turns them into JSON; its editCard function (chapter 3) is a dialogue box for one contact. The organiser uses both exactly as they are.

They are copied into !Org10 as the files Model and Card. The book's examples keep one copy of each, in !Contacts: !Org10 has a file Reuse.list naming the files it borrows, and when the examples are put on the disc each one is copied in, just as Toolkit.list copies the toolkit:

In your own programs, copy the files yourself, and copy them again if you improve the original. This works because Book and editCard were written to know nothing of Contacts' windows: the model/view split of chapter 1 pays off. !Contacts' MainWindow couldn't be reused - it is a window, and the organiser shows contacts differently - but the part that remembers contacts, and the card that edits one, move across untouched.

The section itself, AddressPage, is the organiser's view of the address book, on binder paper: the names under one letter on the left page, the chosen person's details on the right, and a tab for each letter down the right-hand edge - starting below the page's heading and stopping above the turned-up corner, so neither covers the other.

names asks the book for its contacts sorted by surname - list({ sort: 'last' }), from chapter 6 - and keeps those whose name starts with the chosen letter. Each name is recorded with box, so clicking it chooses it:

Typing a letter turns to it, the page corners go to the letter before or after, and a double-click opens !Contacts' card to change the contact. When the card closes, book.put keeps the changed contact, the book emits change, and the window redraws.

One file for everything

The organiser keeps everything in one file of its own type, &1C5, named Organisr (a file type's name can only be eight letters long). Its !Boot is !Contacts' with a different name and number:

The other sections will each keep a list of entries, and they all need the same things: add, change, remove, look up by id, save as JSON, and tell listeners when something changes. So there is one class for all of them, Collection, in the module Store:

It is !Contacts' Book without anything about contacts: a Map from id to entry, nextId for new ones, and a change event. toJSON gives an array of the entries, so a Collection can be handed straight to JSON.stringify.

Trying it

1 Open Examples.JSApps and double-click !Org10, then double-click the organiser file Diary. (If another stage opens it, see the note in chapter 7: start !Org10 first, then drag Diary to its icon.)

2 Click the tabs, or press Ctrl-1 to Ctrl-6. Five of the sections are empty pages with a title.

3 Click the Address tab and type B. Click a name to see the card; double-click it to change it - it's !Contacts' dialogue box.

4 Click the turned-up corners, or press Page Up and Page Down, to go through the letters.

5 Press Insert to add a contact, then F3 to save the file.

Summary

  • Plan a big application the same way as a small one: what it remembers, what happens.

  • The Binder module draws the binder and says what is at a point; the program decides what a click means.

  • A base class can describe an interface: every method the window may call, each doing nothing, so subclasses write only what they need.

  • Sections record where they drew their entries (box), and at finds the entry at a point; findLast searches from the end.

  • Classes are values: a function can return a class expression, and a list of classes can be turned into objects with map.

  • ...array in a call spreads an array into separate arguments.

  • A model written without windows can be reused unchanged by another program: the organiser's Address section is !Contacts' Book and editCard.

  • One file can hold several collections; a generic Collection class serves them all.

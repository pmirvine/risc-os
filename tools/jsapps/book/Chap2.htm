A list you can only look at isn't much use: an application needs a list you can choose from, the way you choose files in a directory display. In this chapter you'll build the second toolkit module, ListView, and use it to show the contacts in columns, with headings, that you can select with the mouse and move through with the keyboard.

What a list needs

Think about how a directory display behaves, and you have the list's plan. RISC OS applications all choose things the same way, and the Style Guide spells it out:

  • Clicking Select on an item selects it, and deselects everything else.

  • Clicking Adjust on an item selects it, or deselects it, leaving the others as they are. That's how you choose several.

  • Clicking Select in an empty part of the window deselects everything.

  • Double-clicking an item opens it.

  • Clicking Menu over an item that isn't selected selects it just while the menu is open (a temporary selection), so the menu can act on it. Chapter 3 uses that.

  • Selected items are shown in reverse: white on black.

And, like any window with a lot in it, the list should scroll, and the keyboard should work: the arrow keys to move up and down, Page Up and Page Down, Home and Copy (End) for the first and last, Return to open.

None of that is about contacts: it's how every list behaves. So it goes in the toolkit, where !Organiser can use it too - for its to-do list, its search results, and more.

You give a ListView the window to fill and a description of the list:

columns
an array of columns, each with a heading (title), a width in pixels, and a function that gives the text to show in it for an item. nameOf and phoneOf from the Model are just such functions; the other two are arrow functions that pick out a field.

key
a function that gives what tells one item from another - here each contact's id. More on this below.

Then list.setItems(array) tells it what to show (MainWindow's refresh gives it the Book's sorted list), and list.on('open', fn) asks to be told when an item is opened. For now, opening a contact just shows a little of it in a message box: chapter 3 opens a proper dialogue box instead. The message box is the desktop's reportError(message, options), the box your programs' mistakes appeared in, in the first book. Its options change how it looks: appName puts Message from Contacts in the title (without it the title is just Error), and category: 'info' shows the "information" picture rather than the warning one. lines.filter(Boolean) keeps only the parts that count as true - the ones that aren't empty or missing - because Boolean(x) is true or false as x counts, so a contact without a company doesn't get an empty gap between two commas.

How ListView works

ListView is about 180 lines, in Toolkit.ListView. It's an Emitter, so it can tell the program when something happens. Here is how it starts:

constructor(win, { columns, key = (x) => x, top = 0 }) takes the object you give it apart straight away: { columns, key, top } in the brackets makes three variables from the properties of the same names. This is called destructuring. key = (x) => x gives a default: if you don't give a key, each item is its own key. (top, the room to leave above the list, is for a toolbar in chapter 5.)

Object.assign(this, { win, columns, key, top }) copies all four onto the ListView in one go - the same as four lines of this.win = win; and so on.

Then the ListView gives the window its redraw function and listens for its events. From here on, the window is the ListView's to manage.

Rows and positions

Every row is ROW (20) pixels high, and the headings take the first row. Two small methods convert between rows and positions:

  • rowY(i) gives the top of row i in the work area.

  • indexAt(y) goes the other way: which row is at height y? Dividing by the row height and rounding down (Math.floor) does it. Finding out what was clicked from where is called hit-testing.

width is a getter, as in chapter 1. It adds up the columns' widths with reduce, an array method that goes through the array carrying a running total: (a, c) => a + c.width is called with the total so far and each column in turn, starting from 0.

The work area's size

setItems keeps the items, and then resize sets the window's extent - the size of its work area - to fit them all, with setExtent. That's what makes the scroll bar work: with ten contacts the extent is no taller than the window, but with a hundred it's much taller, and you can scroll through them. (The window's open event calls resize too, so that making the window wider makes the work area wider.)

Drawing only what shows

A list may have thousands of rows, but only a screenful can be seen. The redraw function is given the visible part of the work area as r (as in the first book), so draw works out the first and last rows in it with indexAt and draws only those. That keeps the list quick however long it grows.

Each row is a background rectangle, then the columns' texts. For a selected row the colours are swapped, black background and white text, as the Style Guide asks. row draws each text clipped to its column (g.clip() after a rectangle limits drawing to that rectangle, until g.restore()), so a long email address can't spill into the next column.

The headings are drawn last, at the top of the visible area (r.y0) rather than the top of the work area, so they stay put when you scroll and cover the rows beneath them.

The selection

The selection is a Set (chapter 1) of the selected items' keys. This is why a ListView needs a key function. The items it's given are replaced each time the list is refreshed - from chapter 3 on, the Book makes a new object for a contact whenever it's changed - so remembering the objects themselves wouldn't work. Their ids stay the same, so remembering the ids does. That's also why setItems removes the keys of any items that have gone, and keeps the rest: the selection survives a refresh.

selected() gives the selected items, in list order, by filtering the items for the ones whose key is in the Set. Every change to the selection goes through changed(), which redraws the list and emits select so the program can, for example, shade menu items that need a selection (chapter 4).

The mouse

click follows the Style Guide's rules. First it ignores clicks on the headings. Then it finds the row with indexAt, and the item there (undefined if the click was below the last row):

  • Menu: if the item isn't selected, it's selected for now and temporary remembers that. Either way, the program is told with a menu event, so it can open its menu. (!!x is two "not"s: it turns any value into true or false as it counts, so temporary is false rather than undefined when there's no item.)

  • Otherwise the list takes the input focus with wimp.setCaret(this.win) (an invisible caret), so that the keys come to it.

  • Select below the last row clears the selection.

  • Adjust adds the item to the selection, or takes it out if it was already there.

  • Select selects just this item.

Returning true tells the Wimp the click has been dealt with. double emits open for a double-click with Select, and drag tells the program a drag has started on the selection (chapter 8 uses it to drag contacts out of the window).

The keyboard

The keys are handled with switch, a neater way of writing a row of ifs that all compare one value: JavaScript compares ev.code with each case in turn and runs the code after the first that matches, up to a break (which jumps out of the switch) or a return; default catches everything else. A case without a break would run on into the next one, so each ends with one.

The keys move the current row: the one last clicked or moved to. findIndex finds its position in the list (or -1 if there isn't one). Each key works out a new position - one up, one down, a page up or down, the first, the last - clamped with Math.max and Math.min so it can't go off either end. Then the new row is selected and ensureVisible scrolls, if it has to, so it can be seen. Return opens the current row.

For any other key, key returns undefined: nothing. As in the first book, that lets the key go on to the rest of the desktop, so F12 and the other keys still work.

ensureVisible compares the row's position with the part of the work area showing (scrollY to scrollY + h, less the headings) and scrolls just far enough, with scrollTo.

Summary

  • Every RISC OS list chooses the same way: Select selects one, Adjust adds or removes one, Select on nothing clears, double-click opens, Menu can select temporarily, the selection is shown in reverse.

  • ListView (the toolkit) draws a list of items in columns on a window, handles the mouse and keyboard, and emits select, open, menu and drag.

  • Hit-testing: work out what's under the pointer from where it is (indexAt).

  • Draw only the rows in the visible area; set the extent to fit all of them so the window scrolls.

  • Remember a selection by the items' keys, not the items, so it survives a refresh.

  • Destructuring ({ columns, key } in a parameter list) picks properties out of an object; = value gives a default; Object.assign copies properties; reduce works through an array keeping a total; findIndex finds a position.

Exercises

1 Show how many contacts are selected in the window's title (Contacts: 3 selected), using the list's select event.

2 Add a Company column between Name and Phone.

3 Make Ctrl-A select every contact. (Its key code is 1. Listen for the window's key event in MainWindow, after the ListView has been made.)

4 Why does ListView's key method return undefined for keys it doesn't use, rather than false?

Answers

1 In MainWindow's constructor: 
this.list.on('select', (items) => {
  if (items.length) w.setTitle(`Contacts: ${items.length} selected`);
  else w.setTitle('Contacts');
});
2 Add a column to the array, and make the window a little wider: 
{ title: 'Company', width: 140, text: (c) => c.company },
3 In MainWindow's constructor, after the ListView: 
w.on('key', (ev) => {
  if (ev.code === 1) { this.list.selectAll(); return true; }
});
4 Returning false would tell the Wimp the key had been dealt with, so it would stop there. Returning nothing lets it go on to the rest of the desktop (as chapter 8 of the first book explained), so keys such as F12 keep working.
